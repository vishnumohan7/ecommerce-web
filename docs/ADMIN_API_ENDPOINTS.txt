19. EXPECTED RESPONSES AND TESTING NOTES
----------------------------------------

Typical success codes:
GET    -> 200
POST   -> 201 or 200 depending on the action
PATCH  -> 200
DELETE -> 200

Typical failure codes:
400 = invalid request JSON or validation failure
401 = missing/invalid token or access denied
403 = permission/policy rejection where applicable
404 = record not found or outside the current store
409 = duplicate, dependency, invalid state transition, capacity or stock conflict
422 = business-rule rejection
429 = rate limit exceeded
500 = unexpected server error; record the x-request-id response header

Representative error envelope:
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request failed",
    "requestId": "<REQUEST_UUID>"
  },
  "path": "/api/v1/example",
  "timestamp": "2026-10-11T10:00:00.000Z"
}

For every destructive or financial test:
1. Create dedicated TEST/POSTMAN records.
2. Save the IDs and original values.
3. Do not delete or modify client records.
4. Use a unique refund idempotencyKey for each intended refund.
5. Repeat the same refund key once to verify that it does not duplicate money.
6. Confirm list pagination metadata: page, pageSize, total and pageCount.
7. Confirm a missing token and a token without the required permission are rejected.

The removed licence and multitenancy APIs are intentionally not included.
Customer storefront, basket, checkout and customer self-service APIs are also
intentionally excluded from this admin-only hand-off.
